# Codex lifecycle integration

Historical lifecycle milestone. See [Phase 5](PHASE5_EVERYDAY_CODEX.md) for current everyday commands, later authenticated evidence, offline verification and remaining limits.

Windows verification: 2026-10-16; Codex CLI **0.162.1**, Node.js **24.17.0**, Rust **1.99.0**, bundled SQLite **3.53.2**. Schema 3 and locked dependencies are unchanged. This document supersedes the lifecycle conclusions in [the earlier readiness milestone](CODEX_READINESS.md).

SwapCtx now provides an opt-in managed Codex console. Actual Codex provider requests contain selected project context at startup, after resumption, after manual compaction, and in an immediate continuation following automatic compaction. These transport checks use a synthetic local provider. **Real-model use of the selected knowledge remains unverified:** the separate evaluation stopped with `authentication_required` before a model request. This is an integration pilot, not unconditional production clearance or demonstrated model adherence.

## Use

Install Node.js 24+ and the tested native Codex CLI version. Authenticate/configure Codex through its own supported workflow. From an initialized SwapCtx project or a nested directory:

```powershell
$SwapCtx = 'C:\path\to\swapctx.exe'
$Codex = 'C:\absolute\path\to\codex.exe'
& $SwapCtx codex setup --codex $Codex
& $SwapCtx codex doctor
& $SwapCtx codex run
# Start a different managed thread, retaining the previous reference:
& $SwapCtx codex run --new
```

Use the same global `--data-dir ABSOLUTE_DIRECTORY` on each command when using an alternate store. The optional `codex --node ABSOLUTE_NODE_EXE` selects a trusted Node executable instead of PATH. The adapter is embedded in the Rust executable; the integration source directory need not be distributed beside it. Ordinary memory commands require neither Node nor Codex.

The console accepts one prompt per line. `/context` previews the local selected packet, `/query WORDS` changes retrieval terms, `/query` clears them, `/compact` requests native compaction, `/new` starts a new thread on the next prompt or compaction, and `/exit` closes the console. Requirements remain selected independently of query terms. Retrieval terms last only for that console invocation; each invocation begins without a query. This is a text console with streamed assistant output, not the full Codex TUI or an attachment/approval interface.

Read-only is the default Codex sandbox. Explicitly choosing workspace writes changes adapter settings:

```powershell
& $SwapCtx codex setup --codex $Codex --workspace-write --replace
# Return to read-only:
& $SwapCtx codex setup --codex $Codex --replace
```

Changed settings require `--replace`; a copy of the previous settings is retained. Requests use Codex's `approvalPolicy: never`; interactive server requests receive an unsupported-method error, never an approval. The wrapper validates the returned sandbox type. Configuration selection and rejection behavior are tested; legitimate workspace edits through this console have not been tested against a real model. SwapCtx rules remain advisory data and manual checks, without tool interception or enforcement.

`setup` does not edit Codex configuration, install hooks, or submit model requests. `doctor` checks version, local context coverage, protocol availability, hook discovery and account availability without a model request. It returns failure for incomplete mandatory context or missing required authentication. Hook discovery does not establish delivery.

## Delivery architecture and observed failures

The official [app-server documentation](https://learn.chatgpt.com/docs/app-server) describes stdio initialization, thread/turn operations, item injection and compaction events. The implementation was checked against schemas generated by the installed 0.162.1 executable and exercised through that executable, rather than assuming every field in newer documentation exists in this release.

The following findings are local runtime observations:

1. Updating `developerInstructions` while resuming a loaded thread did not replace its existing prompt messages. Restarting the app-server alone also left old prompt history. Updating only configuration therefore failed to deliver changed knowledge reliably.
2. A fresh app-server process per managed operation applies current runtime configuration. When the context fingerprint or existing developer policy changes, SwapCtx additionally appends a current, tagged developer message through `thread/inject_items` and waits for acknowledgement before starting the turn. Current configured developer instructions are preserved alongside the external data block.
3. Native compaction reconstructs context using the updated runtime instructions. A fixture summary deliberately containing no saved facts still produced an immediate continuation with the selected packet. A separate test forces native automatic compaction after an unsupported tool response and verifies the outgoing continuation too.

Earlier snapshots may remain in conversation history. The current tagged block is explicitly identified as current; supersession does not erase historical messages or retract knowledge already sent to a provider. Injection acknowledgement and observed provider input are evidence of delivery, not evidence of understanding, correctness, instruction priority compliance or hidden model state.

The official [hooks documentation](https://learn.chatgpt.com/docs/hooks) describes lifecycle hooks and additional context. Local probes discovered enabled hooks but did not demonstrate native SessionStart delivery. Git project fixtures, a no-daemon variant and a PowerShell command variant did not resolve the observed failure. The cause remains undetermined. No native hook is installed or relied upon. Launching ordinary `codex` outside `swapctx codex run` does not activate this managed integration. The earlier [context-first exec launcher](CODEX_READINESS.md#explicit-launcher-use) remains available.

## Retrieval and failure behavior

Before each managed operation, the real CLI produces a fresh [context v1](CONTEXT_PROTOCOL.md) packet with an 8,192-byte complete-output budget and at most 100 records. It excludes stale, invalid, conflicting, unknown-provenance and secret-like knowledge by default. Missing mandatory requirements/rules or a truncated candidate scan stops the operation before any provider request. These are coverage checks; provenance is self-reported and freshness is not proof of truth.

The selected snapshot is held for the duration of a turn, including automatic compaction. Database changes during that turn are picked up on the next managed operation. There is no continuous memory monitor, automatic memory capture or mid-turn database refresh. An 8 KiB packet budget does not bound the whole conversation or expand the model's native context window. Native model-generated compaction is lossy and is not a backup.

Context retrieval has a five-second timeout; ordinary protocol requests have a fifteen-second timeout and turns have a ten-minute timeout. Input is strict UTF-8 with at most 16 KiB per line and 32 queued lines. App-server framing supports fragmented UTF-8 and out-of-order replies, bounds buffered input at 8 MiB and pending requests at 32, and rejects malformed protocol messages. Unsupported versions fail explicitly instead of silently relying on an untested protocol.

Each project/store pair has a separate exclusive lock and atomically published metadata under `DATA_DIRECTORY/codex`. The saved reference is checked against the active Codex home and the thread's original project directory before resumption can override its working directory. Foreign-thread IDs are rejected before a provider request. Locks coordinate these managed clients; they do not coordinate an independently opened Codex TUI.

After an interrupted process, run `swapctx codex recover-lock` only if a lock remains. It removes only a validated marker belonging to a process that no longer exists. Live/unverifiable owners, unexpected contents and symlinks are refused. A reused PID can conservatively prevent recovery. Corrupt or missing thread metadata fails without resetting the store. `/new` or `run --new` retains the prior reference when a valid prior reference exists; it does not repair corrupt files. Preserve files before manual recovery.

`codex --json` emits newline-delimited JSON with `protocol: "swapctx.codex"`, `version: 1`. Events include `integration`, `configured`, `diagnostics`, `context_preview`, `context_selected`, `session_ready`, `text`, `compaction_started`, `compaction_completed`, `turn_completed` and `warning`. Adapter failures emit a structured error code on stderr and exit 1; interruption exits 130 where delivered to the adapter. Rust argument, executable-launch and database failures can occur before the adapter and retain ordinary CLI diagnostics. A `context_selected` event does not certify model receipt or use. Raw backend diagnostics are withheld to reduce accidental exposure; use Codex's own diagnostics separately when a generic protocol error needs investigation.

## Data safety

Retrieval stays local. Using Codex sends selected context and prompts to its configured provider and uses Codex's own authentication, configuration and native history. SwapCtx does not copy credentials into its metadata. Metadata contains executable/project/home paths, thread IDs, fingerprints and timestamps; context and prompts are retained according to Codex's own behavior. The wrapper preserves native configuration bytes in the isolated end-to-end fixture. Actual Codex runtime activity may update its own history, caches or logs.

Local settings, session references, memory databases and backups are plaintext and inherit local permissions. Secret detection is heuristic, not comprehensive redaction. Tagging saved knowledge as untrusted data is not a guaranteed prompt-injection defense. Output controls are escaped for terminal safety, but a model can still generate sensitive text. No secure ACL provisioning, encryption, authenticated provenance or tamper-proof audit is claimed.

SwapCtx SQLite `backup`, `export`, `import` and `restore` cover the documented memory store/bundle. They do **not** include adjacent Codex adapter metadata or native Codex conversation history. Preserve those separately when continuity of a managed thread matters. Restoring memory still permits a fresh managed thread; native conversation reconstruction is not guaranteed by a memory snapshot.

## Reproducible verification

From the source directory, with cached dependencies:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\verify.ps1 `
  -Offline -ReleaseTests -ContextTests -CodexPath 'C:\absolute\path\to\codex.exe'
```

The suites distinguish their evidence:

| Suite | Scope |
| --- | --- |
| Rust fmt / Clippy with warnings denied | Formatting and static checks |
| 47 native tests in both debug and release | Storage, migration, lifecycle, recovery, paths and existing CLI behavior; optional benchmark remains separately ignored |
| 10 supplemental SQL checks | Independent SQL behavior checks using Node SQLite 3.53.0; not a substitute for bundled SQLite tests |
| 19 context/legacy-adapter checks | JSON contract, filtering, coverage, budgets and prior launcher behavior |
| 13 session transport/metadata checks | Malformed frames, invalid encoding, oversized output, disconnects, timeouts, RPC error privacy, fragmented UTF-8, concurrent replies, rejected approvals, atomic publication and packet fingerprints |
| 5 prior native Codex checks | Context-first exec delivery, lifecycle hook negative probes and stale-context refusal |
| 17 native lifecycle checks | Startup, nested-directory resume, manual/automatic compaction, new-thread references, safe settings replacement, version refusal, locks/recovery, invalid console input, query preview, foreign-thread refusal and incomplete-context refusal |

The native Codex suites use isolated temporary homes/projects and a loopback synthetic provider. No real-model reasoning is involved. The automatic compaction fixture deliberately emits an unavailable tool call; it verifies error/compaction recovery and does not demonstrate successful project editing.

The Windows verification command completed successfully: all listed non-model suites passed, as did formatting, Clippy and the release build. A final privacy-disclosure wording correction was followed by another format check, release build and direct disclosure check. The optional performance benchmark was not rerun for this milestone; no new performance claim is made.

The separate real-provider evaluation uses generated, unpredictable release identifiers and a no-context control. It checks startup recall, supersession after resume and new knowledge after compaction, while rejecting observed tool use. It may issue up to five model operations through the user's normal Codex provider/authentication and retain synthetic probe conversations in native history. It does not read actual project memory. Run explicitly after configuring authentication:

```powershell
node scripts/check-model-context.cjs 'C:\absolute\path\to\codex.exe' target/release/swapctx.exe
# Or add -ModelTests to the verification command above.
```

The local attempt returned `authentication_required`, `contextUseObserved: false`, and no completed checks, before any model request. This gate is recorded as blocked, not passed. Even a successful nonce evaluation would establish use in those particular turns, not guaranteed adherence across arbitrary workflows. Automatic mid-turn compaction has transport evidence only; the real-provider probe tests manual compaction and subsequent continuation.

## Readiness decision

Historical decision below: the later [real-world pilot](REAL_WORLD_CODEX_PILOT.md) passed all eight checks in the user's authenticated terminal. [Phase 4](PHASE4_LONG_SESSIONS.md) supersedes current readiness and adds longer-session measurement; natural automatic recovery remains unverified.

Ready for an opt-in managed-console pilot on the tested Windows/Codex/Node versions. Startup/resume/compaction context transport has reproducible native runtime evidence, and prior storage/CLI contracts are preserved. Before claiming normal production Codex usage, complete authenticated model-use and ordinary workspace-edit workflow checks. Native TUI hook delivery, Linux execution, hosted CI and online dependency advisory scanning remain unverified. Measure per-turn app-server startup overhead with a real configured provider before broader release. Expanding agent support or claiming enforceable boundaries is outside this milestone.

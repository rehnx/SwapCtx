# Context protocol v1

`swapctx --data-dir ABSOLUTE_DIRECTORY context --protocol-version 1` emits one compact UTF-8 JSON object and a newline. Success exits 0; operational failure exits 1 with `ok:false`, a stable error code, a generic message, and no records. Clap usage errors retain conventional stderr/exit 2 behavior. Consumers must check exit status, protocol, version, `ok`, scope, and coverage before handing off context. Ignore unknown additive fields; incompatible semantics require a new protocol version. Human-readable commands remain unchanged.

[JSON Schema](schema/context-v1.schema.json) describes success and failure packets. SQLite's bundled JSON encoder performs string serialization; no additional dependency or handwritten quoting implementation is used. JSON-valid terminal controls and bidirectional formatting characters are escaped while preserving parsed content. Database identities are decimal **strings**, preserving all SQLite 64-bit IDs through JavaScript parsing; stable origin IDs remain hexadecimal strings. Unix times are integer seconds, not model measurements. Numeric consumers should use lossless parsing for manually edited out-of-range timestamps.

## Selection and scope

Reads use a single read-only transaction and integrity/provenance checks. The nearest registered ancestor is the scope; registered child projects do not inherit parent records. Schema 3 is required for this new command. Legacy human-readable reads still work; `context` returns `migration_required` without altering older databases. Back up before explicitly migrating with init or a normal write.

Default selection includes active, valid, non-expired records with known self-reported origins, excluding all competing valid active records sharing an explicit key. Requirements (`kind=requirement`, ASCII case insensitive) are considered regardless of query. Other records match any literal whitespace-separated query term across content, kind or key. Requirements rank first, then number of **distinct** matched terms, then descending local ID. Repeated terms, including ASCII case variants, do not multiply their weight. Without a query, optional records rank by local ID. Search uses ASCII case folding; this is lexical ranking, not semantic retrieval. Lifecycle invalidation, archival and supersession remain authoritative exclusions.

Queries accept up to 4,096 UTF-8 bytes and 16 input terms before deduplication. Candidate examination is capped at 5,000, ordered by requirement status and recency before scoring. Older candidates beyond that cap may be more relevant; `scan.truncated` explicitly reports this limitation. Ranking retains lightweight candidate descriptors, sorts once, and serializes candidates as needed for budget selection inside the same read transaction. Whole-store integrity checking and conflict grouping still scale with database size; the cap does not bound all database work. Rules stage at most 101 accepted entries and are never cut in the middle of a pattern. Global rule counts expose any missing rule coverage.

`--include-stale`, `--include-conflicts` and `--allow-unknown-provenance` are explicit review modes. Such records carry weakness flags, increase `review_required_records`, and prevent automatic handoff. They cannot enable sensitive-output disclosure. Secret heuristics inspect kind, content, timestamps, key, source, actor and rule text; matched records/rules are omitted entirely. Heuristics cannot detect every secret. Origins and expiry are self-reported; no expiry means no scheduled expiration, not independently established freshness. An origin label is not authenticated evidence.

## Budgets and coverage

`--max-bytes` ranges from 2,048 to 131,072 (default 32,768); `--limit` ranges from 1 to 100 (default 20). The byte ceiling covers the **complete JSON packet plus newline**, including metadata, rules and escaping. `bytes_used` measures the JSON object without its newline. This is a reproducible UTF-8 budget, not a token count or a promise about a model's available context. Records and rules are omitted whole, never semantically truncated. Rules take priority over records; requirements take priority over optional records. Ranked candidates that cannot fit the complete packet are skipped so smaller lower-ranked candidates can still be returned. The record limit applies to returned records. A few bytes may be reserved for growing omission-counter widths; this is a greedy priority selection, not an optimal knapsack solver or a guarantee of exact budget utilization. Budget pressure can still omit requirements and must be handled explicitly.

`mandatory_context_complete` means every active valid requirement and every project boundary rule was returned, scanning was not truncated, and no included record needs freshness/conflict/provenance review. It does **not** establish truth, model receipt, model adherence, or enforcement. Optional notes can be omitted under the record/byte budget while mandatory coverage remains complete. Consumers needing exhaustive notes must inspect omission counters separately. The included adapters refuse incomplete mandatory coverage instead of silently starting with missing requirements.

Omission counters use one primary exclusion reason per examined candidate, in sensitive/stale/conflict/unknown/budget/limit order. Budget omissions can include rules. `inactive_or_invalid` is a project-wide count; other counters generally describe examined candidates, not every database record. Coverage totals are independent global project counts so excluded requirements cannot silently disappear.

Error codes: `unsupported_protocol`, `invalid_request`, `invalid_storage_path`, `store_unavailable`, `migration_required`, `project_unavailable`, `retrieval_failed`, and emergency `serialization_failed`. Detailed database errors, paths and saved values are withheld from this machine interface; use doctor and existing manual commands for diagnosis. No recovery writes or repairs occur during retrieval.
